# Облако: синхронизация между устройствами

Орбита остаётся local-first: IndexedDB на устройстве — основное хранилище, всё работает без сети. Облако (Supabase) — копия, через которую ваши
устройства обмениваются изменениями. Оно **выключено по умолчанию** и использует **ваш собственный проект Supabase**; никому другому ничего не
отправляется. Вход по почте и паролю: Настройки → «Облако».

## Настройка (один раз)

1. Создайте проект на [supabase.com](https://supabase.com) (бесплатного плана достаточно).
2. Примените схему из `supabase/migrations/` (SQL-редактор или `supabase db push` из CLI), **все файлы по порядку**. Они создают
   `public.sync_rows`, политики RLS и триггеры, приватный бакет `audio` с политиками по папке пользователя и функцию `orbita_sync_push`,
   которая отклоняет устаревшую правку. Проект только с первым файлом работает для обычной синхронизации без шифрования: приложение
   замечает это и пишет по-старому, а шифрование не включит, пока не применён второй файл.
3. Authentication → Providers → Email: для личного приложения удобно выключить «Confirm email» (иначе после регистрации нужно открыть
   письмо). Если оставить включённым, ссылка из письма ведёт на Site URL: укажите в Authentication → URL Configuration адрес, где опубликована
   ваша копия Орбиты, и добавьте его в Redirect URLs (нужно для сброса пароля).
4. Скопируйте адрес проекта и **публикуемый (anon) ключ** в `.env` (см. `.env.example`) до сборки:

   ```bash
   VITE_SUPABASE_URL=https://<ваш-проект>.supabase.co
   VITE_SUPABASE_KEY=<публикуемый anon-ключ>
   ```

   Оба значения публичны по замыслу: доступ защищают политики строк (RLS) и ваш аккаунт. **Никогда не кладите в приложение ключ
   `service_role`.** Без этих двух переменных раздел «Облако» скрыт; `VITE_CLOUD=off` скрывает его, даже если они заданы.
5. Пересоберите приложение и откройте: Настройки → Облако → создайте аккаунт на первом устройстве, на остальных войдите.

## Что синхронизируется

Записи, объекты, люди, проекты, чек-ины, паттерны, обзоры, профиль, пресеты контекста, связи, счётчик расхода ИИ и «надгробия» (окончательно
удалённое). Аудио — отдельными файлами в приватном бакете `audio`.

Не синхронизируется: настройки (ключи ИИ, блокировка, тема), демо-данные, записи в процессе (пустая оболочка записи, «расшифровывается»,
«извлекается»), куски незавершённой записи.

## Как это устроено

- **Сервер:** таблица `public.sync_rows (user_id, tbl, id, data jsonb, ver, target_tbl, updated_at)` с RLS «только своё»; миграции в
  `supabase/migrations/`. Триггеры: серверные часы в `updated_at` (курсор чтения), старая версия не затирает новую (`ver` — собственные
  `updatedAt` / `deletedAt` записи, которые устройство присылает рядом с ней, чтобы их можно было прочитать и у зашифрованной записи),
  «надгробие» убирает названную им запись из облака. Запись идёт через `orbita_sync_push(rows)`: она принимает ещё и версию, на которой
  построена правка (`base`); если облако с тех пор изменилось, запись отклоняется и называется, устройство читает заново (при этом две
  правки сливаются по полям) и отправляет слитую запись, поэтому два устройства, пишущие одновременно, не затрут друг друга.
  Бакет `audio`: `audio/<user id>/<capture id>`, политики по папке пользователя.
- **Клиент:** `src/sync/`: `engine.ts` (слияние и отправка, не знает про Supabase), `supabaseBackend.ts` (адаптер), `service.ts` (вход,
  расписание, realtime, состояние), `rows.ts` (какие таблицы и как версионируются). Служебная таблица `syncmeta` в IndexedDB помнит, какую
  версию каждой записи уже знает облако; изменения находятся сравнением версий, перехватывать записи не нужно.
- **Раунд:** сначала читаем облако (всё, что изменилось после курсора, с запасом 15 с) и сливаем той же логикой, что и импорт копии (побеждает
  более поздний `updatedAt`, надгробия сильнее старых записей); затем отправляем локальные изменения; затем аудио.
- **Когда:** после входа, через 2,5 с после любого локального изменения, по сигналу realtime от других устройств, при возврате на вкладку,
  при появлении сети и раз в минуту. При обрыве связи повтор с нарастающей паузой. Несколько вкладок не синхронизируются одновременно (Web Locks).
- Чужой аккаунт на устройстве не смешивается молча: приложение спрашивает, очистить устройство или объединить.
- «Удалить всё» при входе в облако сначала стирает облачную копию, иначе следующая синхронизация вернула бы данные.

## Шифрование облачной копии (сквозное)

Настройки → Облако → **Шифровать данные в облаке**. На устройстве создаётся случайный 256-битный ключ; каждая запись и каждое аудио
запечатываются им (AES-256-GCM, каждое привязано к своей таблице и id) до отправки, поэтому сервер хранит только то, что не может прочитать,
и никто, кто туда попадёт, тоже. Ключ покидает ваши устройства только вашей рукой:

- при включении один раз показывается **ключ восстановления** (запишите его; позже его можно показать на устройстве, где есть ключ);
- **новое устройство** получает ключ от старого через «Добавить устройство»: обмен кодами (X25519 + ML-KEM-768, так что запись обмена не
  прочитает будущий квантовый компьютер) и 12 контрольных цифр, которые нужно сверить на обоих экранах, либо по ключу восстановления;
- при выходе из аккаунта ключ удаляется с устройства.

Что сервер всё равно видит: таблицу и id записи, когда она менялась, её размер и сам факт удаления. Что перестаёт работать: всё, что читает
ваши записи на сервере (например, подключение к Claude, которое запрашивает облачную копию). Если потеряны все устройства и ключ
восстановления, облачную копию не прочитает никто. Включение запечатывает поверх открытой копии то, что уже в облаке; аудио, которое есть
только в облаке и ни разу не скачивалось на устройство, остаётся как было, пока устройство не откроет приложение и не скачает его.

## Честно о приватности

Пока шифрование не включено, данные в облаке закрыты RLS и паролем аккаунта, но **не зашифрованы вашим ключом**. Владелец проекта Supabase
технически может их прочитать; если проект ваш собственный, это вы. Включите шифрование выше или не входите в облако: приложение полностью
работает локально.

## Проверка

`npx vitest run src/sync`: движок на фейковом облаке с двумя «устройствами» (слияние, гонка с устаревшей правкой, зашифрованные записи и аудио)
и сервис на фейковом клиенте. `scripts/test-sql.sh` применяет все миграции к временной PostgreSQL и проверяет серверные правила из
`supabase/tests/` (CI гоняет их на настоящей PostgreSQL 16; части Supabase заменяет заглушка).
